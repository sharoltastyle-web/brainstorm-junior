# MILESTONES — BrainStorm ג'וניור

תוכנית פיתוח ל־MVP על בסיס `PRD.md`, `ARCHITECTURE.md` ו־`DESIGN.md`, לאחר עדכון הדרישה לסוד יחיד: מפתח AI הנשמר בפיתוח ב־`backend/.env`. קוד המקור ב־GitHub ופריסה אוטומטית ל־Vercel. מסמך זה הוא תוכנית לביצוע עתידי, ולא דיווח על אפליקציה שכבר פותחה.

## סדר הפיתוח והתלויות

| Milestone | שם ותוצר מרכזי | תלות |
| --- | --- | --- |
| M1 | מעטפת מעוצבת ותחילת משחק: בחירת גיל, ניווט ו־Backend עם הפרדת סודות | ללא תלות קודמת. |
| M2 | שאלה ראשונה מקצה לקצה: AI, בחירה אחת ומשוב | השלמת M1 ואישור המשתמש. |
| M3 | המשך משחק: החלפת נושא, מניעת חזרות והתאוששות מתקלה | השלמת M2 ואישור המשתמש. |
| M4 | התקנה כ־PWA ומעטפת Offline | השלמת M3 ואישור המשתמש. |
| M5 | פריסת MVP ל־Production ואימות הגרסה החיה | השלמת M4, אישור המשתמש ותנאי ההפעלה. |

M1 כולל הקמה טכנית הכרחית. M2–M4 הם Vertical Slices של יכולות משתמש, עם UI, לוגיקה, Backend ובדיקות לפי צורכי היכולת; אין חלוקה לאבני דרך נפרדות של Frontend, Backend או Database.

## Development Execution Rules — הנחיות מחייבות ל־AI המפתח

1. יש לפתח את ה־Milestones לפי הסדר שהוגדר במסמך.
2. לאחר השלמת כל Milestone יש לעצור את הפיתוח ולהציג למשתמש את התוצר שהושלם ואת תוצאות הבדיקות מול כל סעיפי ה־Definition of Done שלו.
3. **אין להתחיל בפיתוח ה־Milestone הבא ללא אישור מפורש של המשתמש.** שתיקה או בקשת סטטוס אינן אישור.
4. דיווח ההשלמה כולל קישור ל־Preview או דרך ברורה לבדוק את התוצר, זיהוי Commit/גרסה, תוצאות הבדיקות וחסמים. אין לדווח על בדיקה שלא הורצה כאילו עברה.
5. סעיף Definition of Done שנכשל או נחסם נשאר פתוח. ניתן לתקן בתוך אותו Milestone; מעבר לשלב הבא דורש השלמה או החלטה מפורשת של המשתמש על שינוי ההיקף.
6. אין להוסיף מסכים או פיצ'רים מעבר למקורות. שינוי דרישת מוצר מחייב הצגה למשתמש לפני מימושו.

## כללים משותפים לכל השלבים

- הסוד היחיד שמוגדר לאפליקציה הוא `OPENAI_API_KEY`. בפיתוח הוא נמצא ב־**`backend/.env`**, שנטען ב־Backend בלבד ומוחרג ב־`.gitignore`. אין מפתח בקוד ה־Frontend, ב־bundle, ב־API response, ב־Cache או בלוגים. ב־Git מותר `backend/.env.example` עם ערך ריק בלבד.
- ב־Vercel המפתח מוזן כמשתנה סביבה של ה־Backend; קובץ הסודות אינו מועלה דרך GitHub. ניתן להשתמש במפתחות אותו שירות המופרדים לפי Development/Preview/Production; בכל סביבה מוגדר רק סוג הסוד הזה.
- הפיתוח והבדיקות נעשים ב־Development וב־Preview. פרטי Production נשמרים ב־Vercel בלבד. PR לא מהימן אינו מקבל סודות. עד M5 אין Merge של גרסת המשחק המלאה ל־`main`, שמפעיל פריסת Production.
- לפי ה־Architecture המעודכן **אין Database, Redis, חשבונות, Database Migrations או הקמת שני מאגרי נתונים**. המשחק וה־Seen Set נמצאים בזיכרון הדפדפן בלבד. שינויים בחוזה API ובפורמט Question Ticket נבדקים ב־Development/Preview לפני פריסה, תוך שמירת תאימות לגרסה בתוקף.
- ניסיון יחיד ומניעת חזרות נאכפים בזרימת הממשק. ה־Backend מסתיר ומאמת את הפתרון באמצעות Ticket מוצפן, אך אינו שומר אם נבדק בעבר ואינו מונע מלקוח ששונה לשלוח אפשרות אחרת. אין לבדוק או להבטיח אכיפה אטומית שרתית שאינה קיימת בתכנון.
- ZDR מאושר הוא תנאי לשימוש בנתוני ילדים לפי ה־Architecture. עד לאימותו משתמשים בתוכן סינתטי של מבוגרים בלבד ונתיב הילדים חסום. Fixtures לבדיקות אינם מאגר שאלות של המוצר ואינם הוכחה לחיבור AI חי.
- בכל שלב נשמרים שלושת המסכים בלבד, עברית ו־RTL, ללא ניקוד מצטבר, טיימר, הרשמה או היסטוריה בין ביקורים. העיצוב נבדק מול DESIGN.md והתמונות, ולא מוחלף במסכי דוגמה סטטיים.

## M1 — מעטפת מעוצבת ותחילת משחק

### שם ומטרה

להקים בסיס עובד שבו המשתמש נכנס לאפליקציה, קורא אודות, בוחר קבוצת גיל ומגיע למסך הטריוויה, עם הפרדה תקינה בין Frontend, Backend וסודות.

### מה יש לממש

- Repository פרטי ב־GitHub, React/TypeScript, Vite, CSS Modules ו־Vercel Functions ב־Node.js 24 לפי ה־Architecture. הגדרת lockfile, type-check, lint, בדיקות ליבה ו־Build ב־CI.
- חיבור GitHub ל־Vercel והפקת Preview מענף פיתוח. ה־AI מדריך את המשתמש צעד אחר צעד בפעולות חשבון שאינן זמינות לו, ובקביעת משתנה הסביבה בלי לשלוח את המפתח בצ'אט.
- תיקיית `backend`, טעינת `backend/.env` בשרת בלבד, `.gitignore` ו־`.env.example` ריק. `/api` מכילה adapters ל־Functions, בלי ייבוא מודולי שרת ל־Frontend.
- בית ואודות לפי ה־Design: לוגו, תמונה, טקסט, צבעים, פונטים וניווט תחתון. מסך הטריוויה כולל בשלב זה אזור נושא; יצירת השאלה תושלם ב־M2.
- בחירה יחידה בין 6–8 ל־9–12, התחלת משחק ושמירת הגיל בזיכרון מעל המסכים. אין התחלת משחק ללא בחירה ואין שחזור לאחר רענון.
- פתיחת הסדרת תנאי ZDR אצל ספק ה־AI במקביל לפיתוח סינתטי; אין להציג אישור שטרם התקבל כקיים.

### תוצר מצופה

Preview מעוצב ופעיל של מעטפת שלושת המסכים. אפשר לבחור גיל, לעבור לטריוויה ולקרוא אודות; ה־Backend מוגדר ונטען עם הסוד בצד השרת בלבד. יצירת שאלה עדיין אינה יכולת שהושלמה.

### Definition of Done

- [ ] בחירת כל קבוצת גיל מובילה לטריוויה עם הגיל הנכון; ללא בחירה לא מתחילים. מעבר לאודות וחזרה שומר מצב, ורענון מאפס אותו.
- [ ] בית ואודות תואמים למבנה ולשפה העיצובית, הניווט RTL פועל ואין מסך נוסף או רכיב הרשמה.
- [ ] `git check-ignore` מוכיח ש־`backend/.env` מוחרג; `git ls-files` מוכיח שאינו tracked. קובץ הדוגמה מכיל ערך ריק בלבד ואין מפתח אמיתי בקבצים שב־Git.
- [ ] בדיקת loader/config בשרת מאשרת טעינת המשתנה בלי להדפיסו; בדיקת bundle מאשרת שאינו מגיע ללקוח. משתנה VITE_ אינו מכיל סוד.
- [ ] CI ו־Build עוברים; Push לענף עבודה יוצר Preview. חסר במפתח מטופל בשרת ללא חשיפת ערכו או קריאה מה־Frontend לספק.

## M2 — שאלה ראשונה, תשובה אחת ומשוב

### שם ומטרה

לממש מסלול שלם מבחירת גיל ונושא ועד לשאלה שנוצרה ב־AI, בחירת תשובה אחת בממשק וקבלת משוב והסבר מה־Backend.

### מה יש לממש

- `POST /api/v1/questions` ו־`POST /api/v1/answers`, עם Zod וחיבור לממשק הטריוויה.
- Pipeline מלא: אימות נושא, Moderation, יצירה לפי גיל, Structured Outputs, ביקורת נפרדת, סינון פלט ואישור שאלה אחת עם ארבע תשובות.
- Question Ticket מוצפן לפי ה־Architecture: מפתחות נגזרים זמניים ממפתח ה־AI באמצעות HKDF ו־context נפרדים, AES-256-GCM, nonce ייחודי, גרסה ותפוגה. אין סוד מוגדר נוסף.
- הצגת ארבע תשובות ללא פתרון גלוי, נעילת הבחירה הראשונה לפני בקשת הרשת ובדיקה דטרמיניסטית בשרת. משוב הצלחה/טעות והסבר קצר באותו מסך; בטעות מוצגת התשובה הנכונה.
- מצבי טעינה וכשל ונוסחים בעברית: נושא ריק, לא מובן, לא מתאים, refusal, פלט חסר, סתירה ו־timeout. אין הצגת תוכן חלקי לפני ביקורת.
- HTTPS/Origin/Content-Type, גבולות קלט ו־output tokens, מגבלת ניסיונות, כלל Vercel WAF להגבלת קצב בתוכנית המתאימה ו־logs ללא תוכן או סודות. אין מונה תקציב גלובלי בזיכרון Function.

### תוצר מצופה

אפשר לקבל שאלה משירות AI אמיתי ב־Preview, עם תוכן סינתטי, לבחור תשובה פעם אחת דרך הממשק ולראות משוב אמיתי מהשרת. רצף שאלות והחלפת נושא יושלמו ב־M3.

### Definition of Done

- [ ] מסלול חי של גיל, נושא, יצירת שאלה ומענה עובד בשתי קבוצות הגיל; ההדגמה אינה מסתמכת על Fixtures בלבד.
- [ ] בדיקות מבוקרות מוכיחות שתוצר חסר, ארבע תשובות שאינן שונות, סתירה בביקורת או תוכן שנפסל אינם מוצגים. refusal ו־timeout מסתיימים בהודעה ולא בטעינה אינסופית.
- [ ] נבדקו מענה נכון ושגוי: בשניהם הסבר מותאם לגיל ובטעות פתרון מפורש. לאחר הקליק הראשון אי אפשר לבחור תשובה אחרת דרך הממשק. ה־Backend אינו מפעיל AI לבדיקת התשובה.
- [ ] בדיקת Network ו־bundle מאשרת שאין מפתח או פתרון/הסבר בטקסט גלוי לפני המענה. Ticket אינו Base64 בלבד או JWT חתום עם payload גלוי.
- [ ] Ticket ששונה, מזהה שאינו תואם, אפשרות שאינה קיימת או Ticket שפג נדחים. אותה בחירה עם אותו Ticket מחזירה אותה תוצאה; נבדק גם כשל פענוח אחרי החלפת מפתח.
- [ ] כלל Rate limiting נבדק ב־Preview ו־429 מטופל; נבדקו מגבלות זמן וניסיונות. אין הצגה של התראת תקציב כ־Hard cap שלא נאכף בפועל.
- [ ] בדיקות Vitest/API ו־Build עוברות; דוגמאות עברית לשני הגילים נסקרו בידי מבוגר. ללא אישור ZDR ההדגמה סינתטית ונתיב הילדים חסום.

## M3 — המשך משחק והתאוששות מתקלות

### שם ומטרה

לאפשר משחק חוזר באותו ביקור: עוד שאלות, החלפת נושא וחזרה אליו, ללא שאלות חוזרות בממשק ותוך שימור הבחירה בעת תקלת תקשורת.

### מה יש לממש

- „עוד שאלה באותו נושא” והחלפת נושא דרך השדה הקיים, עם שמירת קבוצת גיל וזיכרון Seen לאורך המשחק.
- השוואת מועמד לפני הצגה מול כל ה־Set המקומי, גם אחרי מעבר לנושא אחר. fingerprint מנורמל ו־factKey אטום, רמזים מוגבלים ל־AI ומועמד חלופי אחד בלבד בסך הכול לבקשת משתמש.
- בקשת יצירה פעילה אחת, requestId ו־revision מקומיים, מניעת לחיצות כפולות והתעלמות מתגובה ישנה. אין טענה ש־requestId שומר receipt בשרת.
- ניתוק לפני או בזמן בדיקת תשובה: שמירת הבחירה ו־Ticket ב־RAM ושליחת אותה בחירה לאחר חזרת חיבור, ללא פתיחת האפשרויות מחדש.
- שינוי גיל בבית מבטל את השאלה הפעילה אך אינו מוחק Seen; מעבר לאודות וחזרה שומר את המשחק. טיפול ב־Ticket שפג או במפתח שהוחלף ללא משוב מומצא.

### תוצר מצופה

משחק מתמשך ב־Preview שבו אפשר להמשיך, לשנות נושא, לחזור אליו ולהתאושש מניתוק, כל עוד הדף חי. כללי הזרימה נשמרים ללא אחסון בשרת או שחזור ביקור קודם.

### Definition of Done

- [ ] נבדק רצף שאלות, מעבר נושא וחזרה לראשון. מועמד כפול שנכפה בבדיקה נפסל לפני תצוגה; נבדקו גם הבדלי פיסוק ו־factKey. Seen אינו מוגבל לחלון התקצירים שנשלח למודל.
- [ ] מוצתה מכסת המועמדים ללא שאלה תקינה וחדשה: מוצגת הודעה מתאימה ואפשר לנסות שוב או לשנות נושא. אין לולאת AI בלתי מוגבלת.
- [ ] לחיצות כפולות אינן יוצרות בקשות מקבילות מה־UI; תגובה ישנה אחרי החלפת גיל/פעולה אינה דורסת את המצב הנוכחי. retry ליצירה אינו מוצג כהבטחה למניעת חיוב נוסף בשרת.
- [ ] נבדקו ניתוק לפני שליחת תשובה ותגובה שאבדה לאחר עיבודה: הבחירה נשמרת ונשלחת שוב ללא אפשרות לבחור אחרת דרך הממשק.
- [ ] שינוי גיל, ניווט לאודות וחזרה ורענון מתנהגים לפי המקורות; אין אחסון משחק ב־localStorage, sessionStorage, IndexedDB או Cookie.
- [ ] בדיקות Ticket שפג/לא ניתן לפענח אינן מציגות נכונות מומצאת. בדיקות הליבה מ־M2 ובדיקות Playwright לתרחישים לעיל עוברות.
- [ ] גבולות Stateless מתועדים בדיווח: נעילת ה־UI אינה חסימת בקשות ידניות עם בחירה אחרת, ואין מדד בדיקה המטעה לגבי יכולת זו.

## M4 — PWA ומעטפת Offline

### שם ומטרה

לאפשר התקנה ופתיחת מעטפת האפליקציה במובייל ללא רשת, תוך שמירת ההבחנה בין מעטפת Offline לבין יצירת שאלות ובדיקת תשובות המחייבות חיבור.

### מה יש לממש

- Manifest בעברית ו־RTL, אייקונים, standalone ו־Service Worker באמצעות Workbox לפי ה־Architecture.
- Precache של כל שלושת המסכים, פונטים, תמונה ואייקונים; API מסוג NetworkOnly ומוחרג מ־fallback.
- הודעת חיבור במסכים הקיימים, ללא Offline queue, Push או Background Sync. אין Cache של שאלות, פתרונות, Tickets או בקשות.
- עדכון Service Worker ללא reload כפוי בזמן משחק וניקוי Cache ישן במועד המתאים.
- בדיקות מובייל מול ה־Design: טיפוגרפיה, מגע, Focus, גלילה בתוכן ארוך, RTL וניווט שאינו מסתיר תוכן.

### תוצר מצופה

PWA ניתנת להתקנה ב־Preview HTTPS. לאחר טעינה ו־Precache מלא אפשר לפתוח את המעטפת ללא רשת; המשחק המקוון חוזר לפעול עם חיבור.

### Definition of Done

- [ ] התקנה ופתיחת standalone נבדקו בדפדפן מובייל תומך; האתר פועל גם בלי התקנה. מתועדות סביבות הבדיקה בפועל ולא מובטחת תמיכה שלא נבדקה.
- [ ] אחרי Precache נותקה הרשת: המעטפת והנכסים זמינים, ומוצגת הודעת חיבור במקום API. אין הבטחת Offline לביקור ראשון שמעולם לא נטען.
- [ ] Cache Storage אינו מכיל מפתח, Ticket, נושאים, שאלות או תשובות. בקשת API אינה מקבלת HTML של מעטפת.
- [ ] ניתוק וחזרת רשת עדיין מאפשרים רק שליחת הבחירה שננעלה ב־UI; ה־Service Worker אינו משדר POST בעצמו.
